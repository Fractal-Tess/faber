# Runtime Architecture

Faber's runtime is built on Linux container technologies to provide secure, isolated execution environments for user tasks. This document explains the internal architecture, security mechanisms, and execution flow.

## Overview

The Faber runtime consists of four main components:

- **Runtime**: Orchestrates task execution and manages the overall execution lifecycle
- **Container**: Creates isolated filesystem and namespace environments
- **Cgroup**: Enforces resource limits (CPU, memory, processes)
- **Task**: Represents individual execution steps with their configuration

```
┌─────────────────────────────────────────────────────────┐
│                      Runtime                             │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │   Container  │  │    Cgroup    │  │  Task Group  │  │
│  │  Isolation   │  │  Resources   │  │  Execution   │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
└─────────────────────────────────────────────────────────┘
```

## Architecture Components

### Runtime

The `Runtime` is the central orchestrator that manages task execution. It's built using the builder pattern for flexible configuration:

```rust
use faber_runtime::{Runtime, RuntimeBuilder, TaskGroup};

let runtime = RuntimeBuilder::default()
    .with_task_group(task_group)
    .with_timeout(Duration::from_secs(5))
    .build();

let result = runtime.execute()?;
```

**Key responsibilities:**
- Spawns a child process for isolated execution
- Coordinates container setup and task execution
- Collects results via IPC (pipes)
- Handles cleanup after execution completes

### Container

The `Container` component creates an isolated execution environment using Linux namespaces and filesystem isolation:

**Namespaces used:**
- **UTS**: Isolates hostname and domain name
- **Network**: Isolates network stack
- **IPC**: Isolates inter-process communication
- **Mount**: Isolates filesystem mount points

**Filesystem setup:**
1. Creates a container root directory
2. Performs bind mounts for read-only access to host paths
3. Executes `pivot_root` to change the root filesystem
4. Creates minimal `/dev` devices (null, zero, random, etc.)
5. Mounts `/proc`, `/sys`, and cgroup filesystems
6. Creates tmpfs mounts for `/tmp` and working directory

**Example container setup:**
```
Host Root
├── /tmp/faber-container-xxxx/
│   ├── oldroot/           # Old root (unmounted)
│   ├── dev/               # Device nodes
│   ├── proc/              # Process filesystem
│   ├── sys/               # System filesystem
│   ├── sys/fs/cgroup/     # Cgroup hierarchy
│   ├── tmp/               # Temporary files (tmpfs)
│   └── opt/faber/         # Working directory (tmpfs)
```

### Cgroup

The `Cgroup` component manages resource limits using Linux cgroups v2:

**Controllers enabled:**
- **cpu**: CPU time limiting
- **memory**: Memory usage limiting
- **pids**: Process count limiting

**Hierarchy:**
```
/sys/fs/cgroup/
├── cgroup.subtree_control    # Root controllers
└── faber/                    # Faber's cgroup
    ├── cgroup.subtree_control
    └── task-xxxx/            # Per-task cgroups
```

Each task gets its own cgroup to enforce resource limits independently.

### Task

A `Task` represents a single execution step with its configuration:

```rust
pub struct Task {
    pub cmd: String,              // Command to execute
    pub args: Option<Vec<String>>, // Command arguments
    pub env: Option<HashMap<String, String>>, // Environment variables
    pub stdin: Option<String>,    // Standard input
    pub files: Option<HashMap<String, String>>, // Files to create
    pub working_dir: Option<String>, // Working directory
}
```

## Execution Flow

### 1. Initialization

When `runtime.execute()` is called:

1. **Ensure cgroup hierarchy**: Creates `/sys/fs/cgroup/faber` if it doesn't exist
2. **Create pipe**: Establishes IPC channel for result communication
3. **Fork process**: Spawns a child process for isolated execution

### 2. Child Process (Container Setup)

The child process sets up the container:

```
1. Unshare namespaces (UTS, NET, IPC,_MOUNT)
2. Mask sensitive paths (/proc, /sys)
3. Bind mount required directories
4. Pivot root to new filesystem
5. Create device nodes
6. Mount filesystems (/proc, /sys, cgroup)
7. Change hostname
8. Create working directory
```

### 3. Task Execution

For each `ExecutionStep` in the task group:

**Single task execution:**
1. Create task-specific cgroup
2. Prepare command with environment and arguments
3. Write files (if specified)
4. Unshare mount namespace
5. Drop privileges (set uid/gid to nobody)
6. Drop all capabilities
7. Apply seccomp filter (planned)
8. Spawn process
9. Add process to cgroup
10. Wait with timeout
11. Collect stdout/stderr
12. Measure resource usage
13. Cleanup cgroup

**Parallel task execution:**
1. Spawn threads for each task
2. Each thread executes independently (same as single)
3. Wait for all threads to complete
4. Collect all results

### 4. Parent Process (Result Collection)

The parent process:

1. Waits for child to exit
2. Reads results from pipe
3. Cleans up container directory
4. Returns `RuntimeResult`

### 5. Security Hardening

During task pre-execution:

```rust
fn pre_execute_task() {
    // 1. Unshare mount namespace
    unshare(CLONE_NEWNS);

    // 2. Mask sensitive paths
    Container::mask_paths();

    // 3. Drop to unprivileged user
    setgid(65534); // nobody group
    setuid(65534); // nobody user

    // 4. Drop all capabilities
    drop_capabilities();

    // 5. Apply seccomp filter
    apply_seccomp_filter();
}
```

## Security Features

### 1. User Isolation

Tasks run as user `nobody` (UID/GID 65534) with no privileges:
- All capabilities are dropped before execution
- Cannot escalate privileges
- Cannot access privileged operations

### 2. Filesystem Isolation

- **Pivot root**: Changes the root filesystem completely
- **Read-only bind mounts**: Host paths are mounted read-only
- **Tmpfs mounts**: `/tmp` and working directory are in memory
- **Masked paths**: `/proc` and `/sys` from host are inaccessible

### 3. Namespace Isolation

- **UTS**: Container has its own hostname ("faber-container")
- **Network**: Isolated network stack (no network access in current implementation)
- **IPC**: Isolated POSIX queues and shared memory
- **Mount**: Isolated filesystem view

### 4. Resource Limits

Enforced via cgroups v2:
- **Memory**: Prevents memory exhaustion attacks
- **CPU**: Limits CPU time usage
- **PIDs**: Prevents fork bombs

### 5. Capability Dropping

All Linux capabilities are dropped before task execution:
```rust
caps::clear(None, CapSet::Effective);
caps::clear(None, CapSet::Permitted);
caps::clear(None, CapSet::Inheritable);
```

### 6. Seccomp (Planned)

Seccomp filters will restrict system calls to:
- Block dangerous operations (mount, clone, etc.)
- Allow only necessary syscalls for task execution
- Reduce kernel attack surface

## Resource Management

### Memory Tracking

```rust
pub struct TaskResultStats {
    pub memory_peak_bytes: u64,     // Peak memory usage
    pub cpu_usage_usec: u64,        // CPU time in microseconds
    pub pids_peak: u64,             // Peak process count
    pub execution_time_ms: u64,     // Wall-clock time
}
```

Memory is measured from cgroup `memory.peak` file.

### Timeout Enforcement

Tasks are killed if they exceed the configured timeout:

```rust
fn wait_with_timeout(child: &mut Child, timeout: Duration) {
    loop {
        match child.try_wait() {
            Ok(Some(status)) => return Ok(status),
            Ok(None) => {
                if elapsed > timeout {
                    child.kill();  // Terminate the task
                    return Err(TaskTimeout);
                }
                sleep(100ms);
            }
        }
    }
}
```

## Error Handling

The runtime uses comprehensive error types:

```rust
pub enum FaberError {
    ContainerSetupFailed { error: String },
    Fork { e: nix::Error },
    Mount { e: nix::Error, details: String },
    ExecuteTask { e: std::io::Error, details: String },
    TaskTimeout { timeout_duration: Duration, details: String },
    // ... and more
}
```

Errors are propagated through the Result type and serialized for JSON responses.

## Result Serialization

Results are serialized as JSON and sent through a pipe from child to parent:

```rust
// Child process
let result = runtime_result;
serde_json::to_writer(pipe_writer, &result);

// Parent process
let result: RuntimeResult = serde_json::from_reader(pipe_reader);
```

This ensures clean IPC without shared memory.

## Task Group Execution

Tasks are organized into execution steps:

```rust
pub type TaskGroup = Vec<ExecutionStep>;

pub enum ExecutionStep {
    Single(Task),           // Execute one task
    Parallel(Vec<Task>),    // Execute tasks concurrently
}
```

**Example:**
```json
[
  { "cmd": "/bin/sleep", "args": ["1"] },
  [
    { "cmd": "/bin/echo", "args": ["a"] },
    { "cmd": "/bin/echo", "args": ["b"] },
    { "cmd": "/bin/echo", "args": ["c"] }
  ],
  { "cmd": "/bin/echo", "args": ["done"] }
]
```

This executes:
1. `sleep 1` (sequential)
2. Three `echo` commands in parallel
3. `echo done` (sequential, after parallel tasks complete)

## Performance Considerations

### Fork Overhead

The runtime forks once per execution, not per task:
- Container setup happens once
- Tasks share the isolated environment
- Reduced overhead compared to per-task containers

### Memory Efficiency

- Tmpfs for `/tmp` and working directory (in-memory)
- Cgroup cleanup after each task
- No persistent storage between executions

### Parallel Execution

Parallel tasks use threads, not processes:
- Lower overhead than forking
- Share cgroup configuration
- Independent resource tracking

## Configuration

### Default Values

```rust
impl Default for RuntimeBuilder {
    fn default() -> Self {
        Self {
            timeout: Duration::from_secs(5),
            container: Container::default(),
            cgroup: Cgroup::default(),
```

## Limitations and Future Work

### Current Limitations

1. **Root required**: Container setup requires root privileges
2. **No networking**: Network namespace is isolated but not configured
3. **Seccomp disabled**: System call filtering is not yet implemented
4. **Single host**: No distributed execution support

### Planned Improvements

1. **Rootless mode**: Use user namespaces for unprivileged operation
2. **Seccomp filters**: Restrict system calls for better security
3. **Network support**: Configure network interfaces in containers
4. **Caching**: Cache container layers for faster startup
5. **Resource presets**: Predefined configurations for different workloads
